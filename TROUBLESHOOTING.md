# Troubleshooting

Notes on environment issues hit while building/running the `samples/*` programs on
2026-09-05, none of which are bugs in this repo's code — all are local machine
configuration. Kept here as a build-environment reference, separate from the memoria.

## 1. `go generate`/`go build` fails with a DNS lookup error

```
go: downloading golang.org/x/sys v0.30.0
.../errno_linux.go:6:2: golang.org/x/sys@v0.30.0: Get "https://proxy.golang.org/...":
dial tcp: lookup proxy.golang.org on [::1]:53: read udp [::1]:...->[::1]:53: read: connection refused
```

**Root cause:** `/etc/resolv.conf` had no `nameserver` line at all (just the
`# Generated by NetworkManager` comment). Tools that resolve DNS through
NSS/D-Bus (`curl`, `git`, `getent`) kept working fine because they talk to
`systemd-resolved` directly and never look at `resolv.conf`'s content — only
tools that read `resolv.conf` themselves (Go's own resolver, used by
`go mod download`) broke. `resolvectl status` confirmed this: `resolv.conf
mode: foreign`, meaning something other than `systemd-resolved` was managing
the file (in this case, NetworkManager, writing an empty one).

This started after a `systemd` (258.2→260.1) + `networkmanager` (1.54.2→1.56.0)
upgrade on 2026-04-11 (see `/var/log/pacman.log`) — a regression in how that
NetworkManager version auto-detects `systemd-resolved` integration. It went
unnoticed for months because nothing needed a *fresh* `go mod download` in the
meantime (everything was already in the local module cache).

**Fix (applied):**
```bash
sudo ln -sf /run/systemd/resolve/stub-resolv.conf /etc/resolv.conf
```
This points `resolv.conf` at `systemd-resolved`'s local stub (`127.0.0.53`),
which already knows how to reach real DNS servers (`resolvectl status` showed
Quad9/Cloudflare as configured fallbacks).

**Fix (durable, not yet applied):** the symlink above can get overwritten again by
NetworkManager after a reboot or NM restart. To make NetworkManager delegate DNS to
`systemd-resolved` explicitly instead of relying on auto-detection, add under `[main]`
in `/etc/NetworkManager/NetworkManager.conf`:
```ini
[main]
dns=systemd-resolved
```
then `sudo systemctl restart NetworkManager`.

## 2. `samples/printk` fails to compile with a `stubs-32.h` error

```
In file included from samples/printk/code.bpf.c:2:
In file included from /usr/lib/clang/22/include/stdint.h:56:
...
/usr/include/gnu/stubs.h:7:11: fatal error: 'gnu/stubs-32.h' file not found
```

**Root cause:** `samples/printk/code.bpf.c` is the only basic sample that
`#include`s plain libc headers (`<stdint.h>`, `<stdbool.h>`) rather than only
`vmlinux.h` + the `bpf/*` headers. When `clang` compiles for the `bpf` target,
`features.h`'s logic for picking a stub header (32-bit vs 64-bit vs x32) doesn't
resolve the way it would for a normal x86_64 host compile, and ends up wanting
`gnu/stubs-32.h` — part of the 32-bit (multilib) glibc package, which isn't
installed by default on Arch (`[multilib]` ships disabled in `/etc/pacman.conf`).

**Fix:**
```bash
sudo sed -i '/\[multilib\]/,/Include/s/^#//' /etc/pacman.conf
sudo pacman -Sy
sudo pacman -S lib32-glibc
```

## 3. `go build` fails with "C source files not allowed when not using cgo or SWIG"

```
package .../samples/sample_printk: C source files not allowed when not using cgo or SWIG: code.bpf.c
```

**Root cause:** each sample directory has its `.bpf.c` source sitting next to
the Go files. If `CGO_ENABLED=1` (the default here, since `gcc` is installed),
Go's build tooling treats that `.c` file as a cgo source belonging to the Go
package and tries to build it as such — it isn't one, it's only ever meant to
be compiled out-of-band by `bpf2go`/`clang` (via `go generate`), not by `go
build` itself. With `CGO_ENABLED=0`, Go ignores `.c` files in the package
entirely, which is what these samples actually expect.

**Fix:** always build these samples with cgo explicitly disabled:
```bash
CGO_ENABLED=0 go build -o <name> .
```

## 4. Don't build (or `go generate`) as root

Only *running* the compiled binary needs `sudo` (loading an eBPF program into
the kernel requires `CAP_BPF`/root via the `bpf()` syscall). Building with
`sudo go build ...` creates root-owned files under `~/go/pkg/mod` and
`~/.cache/go-build`, which then breaks subsequent normal-user `go build`/`go
generate` calls with permission errors. If that already happened:
```bash
sudo chown -R "$USER:$USER" ~/go/pkg/mod ~/.cache/go-build
```

## 5. Where to watch the actual output

`bpf_printk`/`bpf_trace_printk` output goes to the kernel's trace ring buffer,
not stdout. Watch it live in a separate terminal while the sample runs:
```bash
sudo cat /sys/kernel/tracing/trace_pipe
```
(`/sys/kernel/debug/tracing/trace_pipe` is the same tracefs, kept for backwards
compatibility — either path works.)

## Quick reference: full build+run cycle for a sample

```bash
cd samples/<name>
go generate ./...              # runs bpf2go: compiles code.bpf.c -> code_bpfel.o + .go bindings
CGO_ENABLED=0 go build -o <name> .
sudo ./<name>                  # Ctrl+C to stop
# in another terminal:
sudo cat /sys/kernel/tracing/trace_pipe
```
